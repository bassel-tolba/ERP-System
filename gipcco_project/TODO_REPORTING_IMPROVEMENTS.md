# Reporting Module Improvement Plan

This document outlines known issues and potential improvements for the reporting module.

## 1. Unresolved Issue: Reporting Discrepancies from Transaction Reversals

### Problem Description

Currently, when a transaction with a financial impact is cancelled or reversed (e.g., cancelling a `FinishedProductDispatch`), the system correctly creates a reversing journal entry. This ensures that the **General Ledger and financial statements (like the Trial Balance and P&L) are always accurate**, as the debits and credits of the original and reversing entries cancel each other out.

However, operational reports like the **A/R Aging Report** and **Customer Statement** do not reflect these reversals correctly. These reports are generated by re-aggregating source documents (`CustomerInvoice`, `Payment`, `CustomerCreditMemo`) rather than summing up the General Ledger.

**Example Scenario:**
1. A `FinishedProductDispatch` is created, generating a JE that debits A/R for $100.
2. A `CustomerInvoice` is created from this dispatch. The A/R Aging report now shows $100 due.
3. The dispatch is cancelled. A reversing JE is created that credits A/R for $100.
4. **Result:**
    - The General Ledger balance for A/R is correctly $0.
    - The A/R Aging report still shows the `CustomerInvoice` as open and $100 due, because the invoice itself was not marked as "cancelled" or "reversed". This creates a confusing discrepancy between financial and operational reports.

### Proposed Solution

To resolve this, we need a mechanism to link a transaction reversal back to the original source documents and flag them appropriately.

1.  **Flagging Source Documents:** When a transaction is reversed, the service responsible for the reversal should also be responsible for updating the status of the related source documents.
    *   For a `FinishedProductDispatch` cancellation, if an associated `CustomerInvoiceItem` exists and the invoice has not been paid, the invoice's status should be changed to `CANCELLED`.
    *   If the invoice contains other items, the specific `CustomerInvoiceItem` should be cancelled, and the `total_amount` of the invoice should be recalculated.

2.  **Enhance the `TransactionCorrection` Model:** The `TransactionCorrection` model could be enhanced to store a direct link not just to the reversed object (e.g., the `Dispatch`) but also to the primary financial document it affects (e.g., the `CustomerInvoice`).

3.  **Update Report Queries:** The queries in `ar_reports.py` and `sales_reports.py` must be updated to explicitly filter out any records with a `status` of `CANCELLED`.

This is a significant change that requires careful implementation to ensure data integrity, so it has been deferred for now.
